T1 (P1): IRT theta persistence and retrieval

Why. The app estimates ability per subject on the device and sends it on session_end; nothing stores it, so a new device starts from zero.

  2. Files to change. routers/sync.py (new write step), mastery_read.py (new read_ability), tests/test_sync_engine.py (new tests).
  3. Tables. Option A (recommended, no migration): user_cognitive_profiles.subject_profiles JSONB, under the existing quant and di keys; do not write the flat theta/theta_se (see section G, D1). The row is not created at registration (every reader uses LEFT JOIN), so the writer must upsert: INSERT INTO user_cognitive_profiles (user_id, subject_profiles) VALUES (...) ON CONFLICT (user_id) DO UPDATE SET subject_profiles = .... Option B (alternative): a new table learner_ability (user_id, device_id, subject, state JSONB, client_timestamp, source_event_id, PK (user_id, device_id, subject)), in docs/proposals/IRT_THETA_PERSISTENCE.md; it keeps per-device rows and leaves merging to the client, at the price of a migration.
  4. Migration. None for Option A.
  5. Routes. Write: existing POST /api/v1/sync (no new route). Read: additive field on GET /api/v1/practice/mastery.
  6. Request (already sent by the app, only for subjects the backend named; the app never sends an unclassified estimate):
{ "event_type": "session_end", "event_id": "…", "client_timestamp": 1793879995000, "session_id": "…",
  "metadata": {
    "technique_states": { "…": "…" },
    "theta": {
      "quant": { "subject": "quant", "theta": 0.4, "se": 0.3, "n": 3,
                 "responses": [ { "problemId": "t101", "a": 1.0, "b": 0.0, "correct": true } ] },
      "di":    { "subject": "di", "theta": -0.2, "se": 0.4, "n": 1,
                 "responses": [ { "problemId": "t240", "a": 1.2, "b": 0.5, "correct": false } ] }
    } } }
  1. Response (additive on /practice/mastery; existing keys unchanged):
{ "technique_states": { "…": "…" }, "selection": { "…": "…" }, "as_of": "2026-11-06T10:00:00Z", "devices": 2,
  "theta": {
    "quant": { "theta": 0.4, "se": 0.3, "n": 25, "responses": [ { "problemId": "t101", "a": 1.0, "b": 0.0, "correct": true } ] },
    "di":    { "theta": -0.2, "se": 0.4, "n": 12, "responses": [] }
  } }

A learner with nothing stored gets "theta": {}. A subject that has no data is absent (not null).

  1. Auth. Bearer JWT; a learner reads and writes only their own row (user["id"]).
  2. Validation (a state failing any rule is skipped; the event itself is still stored, a bad theta must never reject a session_end): subject in {quant, di} only (any other key is dropped, never mapped); theta finite in [-3, 3]; se finite and > 0; n an integer in [0, 200] equal to len(responses); responses at most 200 objects {problemId: non-empty string, a: 0.5..2.5, b: finite, correct: boolean}; at most one response per problemId.
  3. Idempotency and multi-device merge (deterministic, documented). Only an event that was stored just now (inserted) writes. Per subject, under the existing per-learner advisory lock: merged.responses = the stored responses followed by the incoming ones, removing a repeated problemId (the first occurrence wins), keeping the latest 200. This is order-independent for evidence (a replayed or older event adds nothing already present), so no timestamp guard is needed. theta and se are informational: the app rebuilds both from responses with the vendored engine, so the server need not port the IRT code; store them from whichever state has the larger n (a tie goes to the incoming state). Never average two estimates. If the server later ports the IRT, recompute here.
  4. Tests. Valid persistence for quant; separate quant and di storage; invalid payloads skipped without rejecting the event (theta 5, n not equal to the response count, 201 responses, correct not boolean, unknown subject); a duplicate event_id writes nothing; two devices with disjoint responses produce the union; a replayed older event changes nothing; the mastery response contains theta and the old keys; an old client (no theta) is unaffected; test_legal_claims still passes (nothing writes the flat theta).
  5. Deploy / rollback. Additive. Deploy the backend first; the app reads theta only when present. Rollback: remove the write step and the response key; stored JSON is harmless.

Frontend status. Ready and tested: remoteAbilityOf, mergeBook, loadAbilityBook (src/lib/learning/ability-book.ts, src/services/learner.ts). It ignores any theta that is not the shape above and rebuilds each state from responses, so a wrong server theta cannot corrupt it. Waiting for backend deployment.

D. Backend verification checklist

  • Existing routes still work, and old frontend clients (no device_id, no theta, no subject handling) remain compatible.
  • JWT authentication and learner ownership hold on every new field and route.
  • Duplicate sync events do not duplicate updates (snapshots, theta, calibration, review, history).
  • Multiple devices never overwrite newer learner progress (T0 tests).
  • Partial event rejection stays per event and the rest of the batch is stored.
  • Existing database data is preserved by every migration; migrations run on a copy of staging first.
  • Payload limits support the realistic mastery snapshot (T0).
  • All tests pass against the real database model, including test_legal_claims unchanged.
  • Staging responses match the contracts above.

E. Acceptance criteria

A backend task is not complete until: it is merged; any migration is applied successfully; its tests pass; its request and response examples are documented here or updated; staging verification is done or explicitly marked pending; and the frontend can consume it with no guessing and no mock values. A written plan or a proposed schema is not completion.

Live finding: why Explorer sub-topics show no techniques (T3)

Short answer. This is a backend data gap, not a frontend bug. The two endpoints the Explorer reads use different vocabularies and nothing links them. This section is the evidence behind T3. Checked 2026-11-06 against https://examarena-staging.duckdns.org for domain=cat.

What the backend returns

EndpointWhat it givesExample
GET /api/topics?domain=catExam topics, each with sub-topic names only (subtopic_list). No technique ids, no link to skills."Quantitative Aptitude" → ["Arithmetic", "Algebra", "Geometry", "Modern Math", "Number Systems"]
GET /api/practice/techniques?domain=cat&limit=50065 :Skill nodes with their own topic and sub_topic.Arithmetic → Fractions and Decimals; topics seen: Arithmetic, Algebra, NumberTheory, Geometry, Logic, Statistics

There is no field that connects "Quantitative Aptitude → Arithmetic" to the Arithmetic skill. Matching by name would be a guess ("NumberTheory" vs "Number Systems"), so the frontend does not do it.

What the Explorer does today

  • The Topics subject shows exam topics and sub-topics as display-only nodes (src/services/explorer-tree.ts).
  • The skills appear as their own subjects (Arithmetic, Algebra, …); there, each sub-topic does contain its techniques.
  • The two vocabularies are deliberately never merged.

What the backend needs to add

Either of these closes the gap (this is the T3 contract):

  1. A skills[] (and reference_ids[]) list for each sub-topic in /api/topics, as in T3 above.
  2. Or an exam topic / exam sub-topic field on every skill in /api/practice/techniques.

Stopgap, if wanted: a hand-written map from CAT sub-topic names to skill names in the frontend. It would go stale whenever the backend renames anything, so it is not added unless requested.
