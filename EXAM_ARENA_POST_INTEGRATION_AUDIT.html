    Prioritized recommendations

    1. Verify and harden onboarding persistence (FE-1, BE-1): run save → logout → login on a disposable account; backend documents null/empty semantics, enums, storage.
    2. Fix Sprint sessions (FE-2): move to the POST slot contract (currently 0 items for most skills).
    3. Make mastery move (BE-2, FE-6): server-side mastery from attempts or ship the BKT engine.
    4. Durable offline queues (FE-3): persist attempts and profile saves; never delete queued work after max retries.
    5. Secure native token storage (FE-4): move off localStorage; review allowBackup.
    6. Android runtime verification (FE-18): run the plan in this report on a device.
    7. Payments (BE-3, FE-7): configure a provider; wire checkout.
    8. Mock exam completeness (BE-4, FE-5): typed answers, passages, sectional mode, score breakdown.
    9. Multiplayer (BE-5, FE-12): publish the Socket.IO protocol; add a client.
    10. Real-mode data cleanup (FE-8, FE-9, FE-13, FE-14): history filters, feature-flag awareness, testimonials, constants out of lib/mock.

    Final integration readiness

    Methodology and limitations

    • Static inspection: frontend source (production and test files), Git diff, backend routers/schemas/migrations/flags/game-server auth, and a scanner that matched every literal API path in src/ to the 122 OpenAPI operations.
    • Runtime verification: read-only calls with the test account (GET probes, auth and refresh, CORS preflights, Socket.IO handshake, content-read session requests). No tokens, passwords or personal data are included in this report.
    • Not executed: all write operations (registration, profile save, practice sync, mock exam configure/submit, friend responses, logout, checkout), backend test execution (needs Postgres and Neo4j), Android runtime, real browser flows with a signed-in session. Playwright suites seed a fake session and test layout/accessibility only.
    • Known gap: the local backend copy lacks PATCH /auth/me; staging runs newer code, so that route's behaviour comes from OpenAPI and earlier probes.
    • Distinction: "Runtime verified" means a real request succeeded; "static" means code and unit tests only.
